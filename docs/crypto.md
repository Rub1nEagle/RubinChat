# Криптография

В этом разделе описано, как именно реализованы три алгоритма ГОСТ и как
они «склеены» в общий асинхронный фасад. Все реализации находятся в
[`backend/app/crypto/`](../backend/app/crypto/) и используют **только**
стандартную библиотеку Python.

> **Важно.** Реализации не защищены от атак по времени и не проходили
> аудит. Они оптимизированы под Python (т-таблицы для Стрибога и
> ГОСТ 28147), но всё равно не constant-time. Для учебной задачи этого
> достаточно, для боевой — нет.

## Стрибог (ГОСТ 34.11-2012)

Стрибог — это хеш-функция с двумя режимами: 256 и 512 бит. Прототип
реализует оба, но в проекте используется только 256-битный (для подписи
и для деривации ключей).

### Структура алгоритма

Хеш строится по схеме Меркла–Дамгора с дополнительным финалированием по
длине и контрольной сумме `Σ`. На каждой итерации внутренний 64-байтный
вектор `h` пропускается через функцию сжатия `g_N(h, m)`.

Внутри `g_N` есть собственный «блочный шифр»: 12 раундов, каждый — это
композиция трёх преобразований:

| Обозначение | Что делает | Где |
| --- | --- | --- |
| `S` | побайтная подстановка через PI | [`streebog.py`, `_S`](../backend/app/crypto/gost3411/streebog.py) |
| `P` | перестановка байтов по таблице TAU | `_P` |
| `L` | линейное преобразование над GF(2) — умножение 8 64-битных подвекторов на матрицу A | `_L` |

Они объединяются в `LPS = L∘P∘S` и применяются к раунд-ключу и состоянию.

### Особенности реализации

* Все константы (`PI`, `TAU`, `A`, `C[0]..C[11]`) перенесены из RFC 6986
  «как есть» в [`constants.py`](../backend/app/crypto/gost3411/constants.py).
* Сообщение обрабатывается **с конца к началу** — как и предписывает
  стандарт. Внутри блока байты интерпретируются как little-endian число
  при сложениях `N` и `Σ`.
* Дополнение: остаток `M` длиной `L` бит превращается в блок
  `0...0 || 1 || M`, где `1` стоит сразу за концом исходных данных.
* Для 256-битного варианта IV = `0x01 * 64`, а на выходе берётся первые
  32 байта. Это **не совпадает** с big-endian truncation в RFC-векторах:
  проект использует little-endian-конвенцию для финальной обрезки. Все
  существующие подписи и conversation-keys опираются на это поведение.
* CPU-bound вызовы укрыты за `asyncio.to_thread`, чтобы не блокировать
  event loop.

### Оптимизация — T-table

Спецификационная реализация `_L` пробегает 64 бита на каждый из 8
8-байтных чанков — около 512 тестов битов и XOR'ов на блок. Слой
[`streebog.py`](../backend/app/crypto/gost3411/streebog.py) собирает
**восемь предвычисленных таблиц `_T_PI[k][b]`** размера 256 64-битных
интов. Каждая таблица фиксирована для своей позиции байта в 64-байтном
блоке и уже включает в себя подстановку PI и линейное преобразование
строки матрицы `A`. Тогда `_LPS(x)` — это 64 индексирования + 56 XOR
на блок, упакованных одним вызовом `struct.pack(">8Q", ...)` в
итоговые байты.

Скорость хеша возрастает примерно в **14 раз** относительно наивной
реализации (на 500 КБ блобе — ~9.7 с → ~0.7 с).

### Self-test на старте

Чтобы оптимизация не «протекла» в подпись и расшифровку,
[`streebog.py`](../backend/app/crypto/gost3411/streebog.py) при импорте
прогоняет:

* `_LPS` против эталонной `_LPS_ref` (битно-идентичная неоптимизированная
  версия) на нескольких случайных 64-байтных блоках;
* end-to-end `streebog_256` / `streebog_512` против эталонной hash-функции,
  собранной из `_LPS_ref`, на 10 разнодлинных входах.

Если результаты разойдутся — модуль падает с `RuntimeError`, и сервер
не стартует. Это безопаснее, чем полагаться только на отдельные
юнит-тесты.

## Блочный шифр (ГОСТ 28147-89)

Это сеть Фейстеля с 32 раундами над 64-битным блоком и 256-битным
ключом. Реализован в современной редакции с фиксированными S-боксами
(CryptoPro A-ParamSet).

### Раундовая функция

Для 32-битной половины `R` и подключа `K`:

```
f(R, K) = ROL11( S( (R + K) mod 2^32 ) )
```

* Сложение по модулю 2³² — обычный целочисленный плюс.
* `S` — восемь параллельных 4-битных S-боксов; индекс 0 применяется к
  младшему ниблу, индекс 7 — к старшему.
* `ROL11` — циклический сдвиг влево на 11 бит.

### Расписание ключей

256-битный ключ режется на восемь 32-битных подключей `K_0..K_7`.
Порядок их использования по раундам:

* раунды 1–24: `K_0, K_1, ..., K_7, K_0, ..., K_7, K_0, ..., K_7`
* раунды 25–32: `K_7, K_6, ..., K_1, K_0`

Дешифрование использует те же подключи, но в обратном порядке (см.
`_round_order_decrypt` в [`cipher.py`](../backend/app/crypto/gost28147/cipher.py)).

### Оптимизация — T-table раундовой функции

[`cipher.py`](../backend/app/crypto/gost28147/cipher.py) собирает **четыре
таблицы `_T0..._T3`** размера 256 32-битных интов. В каждой записи уже
вшиты:

* подстановка `S` (две из восьми 4-битных таблиц на байт);
* битовый сдвиг на правильную позицию байта внутри 32-битного слова;
* финальный циклический сдвиг `ROL11`.

Тогда раундовая функция превращается в

```python
def _f(x, k):
    s = (x + k) & 0xFFFFFFFF
    return _T0[s & 0xFF] ^ _T1[(s >> 8) & 0xFF] \
         ^ _T2[(s >> 16) & 0xFF] ^ _T3[(s >> 24) & 0xFF]
```

— четыре lookup'а и три XOR'а вместо восьми ниблов и отдельной
ротации. Self-test на импорте сравнивает `_f` против эталонной
ниблной реализации `_f_ref` на 64 случайных входах и проверяет
roundtrip `encrypt → decrypt`.

Скорость на 500 КБ блобе примерно в **4.5 раза** выше наивной (CTR на
один блок ~2 мкс вместо ~10).

### Режим CTR

Для шифрования произвольной длины используется простой CTR-режим
([`ctr.py`](../backend/app/crypto/gost28147/ctr.py)):

1. 8-байтный nonce интерпретируется как big-endian счётчик.
2. Подключи `K_0..K_7` вычисляются один раз перед циклом.
3. На каждый блок 32 раунда Feistel **заинлайнены** прямо в цикл с
   локальными биндингами таблиц — это убирает оверхед на вызовы
   функций и обращение по точке. Выход блока упаковывается через
   `struct.Struct(">Q").pack`.
4. Финальный XOR keystream'а с данными делается **одним** вызовом
   `(int.from_bytes(data, "big") ^ int.from_bytes(ks, "big")).to_bytes(...)`.
   Эти три операции на C-уровне Python и для 500 КБ-блоба занимают
   единицы миллисекунд (вместо Python-цикла на ~500 мс).

Шифрование и расшифровка — одна и та же операция XOR с гаммой,
никакого паддинга не нужно.

## Подпись (ГОСТ 34.10-2012)

Электронная подпись на эллиптической кривой над простым полем. Прототип
использует один набор параметров — `id-tc26-gost-3410-2012-256-paramSetA`
из RFC 7836:

| Параметр | Значение |
| --- | --- |
| `p` | `0xFFFF…FD97` (256 бит) |
| `a` | `0xFFFF…FD94` |
| `b` | `0xA6` |
| `q` | порядок подгруппы (256 бит) |
| `G` | `(1, 0x8D91…1E14)` |

### Арифметика точек

В [`ec.py`](../backend/app/crypto/gost3410/ec.py) реализованы:

* `point_add(P, Q, curve)` — сложение, с особым случаем удвоения и
  обработкой бесконечно удалённой точки (представляется как `None`).
* `scalar_mult(k, P, curve)` — алгоритм «double-and-add» (не constant-
  time).
* `is_on_curve` и `point_neg` — для тестов и удобства.

Модулярное обращение использует `pow(x, -1, p)` (Python 3.8+).

### Подпись и проверка

Алгоритм совпадает со спецификацией:

```
sign(M, d):
    e = int(streebog_256(M)) mod q   # если 0 — берём 1
    цикл:
        k ← random_in [1, q-1]
        C = k·G
        r = C.x mod q
        s = (r·d + k·e) mod q
        если r ≠ 0 и s ≠ 0 — выходим
    return r || s

verify(M, sig=r||s, Q):
    проверить 0 < r < q, 0 < s < q
    e = int(streebog_256(M)) mod q или 1
    v = e^(-1) mod q
    z1 = s·v mod q
    z2 = -r·v mod q
    C = z1·G + z2·Q
    return C.x mod q == r
```

Каждый компонент подписи кодируется в 32 байта big-endian, подпись
целиком — 64 байта.

## Асинхронный CryptoProvider

[`provider.py`](../backend/app/crypto/provider.py) — единственная точка,
через которую остальные слои общаются с крипто. Это инстанс класса
`CryptoProvider`, экспортируемый как глобальный `provider`.

API:

```python
priv, pub = await provider.generate_keypair()  # (32 байт, 64 байта)
sig       = await provider.sign(data, priv)    # 64 байта
ok        = await provider.verify(data, sig, pub)
ct        = await provider.encrypt(pt, key, nonce)
pt        = await provider.decrypt(ct, key, nonce)
digest    = await provider.hash(data)          # 32 байта
nonce     = provider.random_nonce()            # 8 случайных байт (sync)
key       = provider.random_session_key()      # 32 случайных байта (sync)
```

### Кодировка ключей и подписей

* **Приватный ключ** — 32 байта big-endian (скаляр `d`).
* **Публичный ключ** — 64 байта: `x || y`, каждый по 32 байта big-endian.
* **Подпись** — 64 байта: `r || s`.
* **Хеш** — 32 байта (Стрибог-256).

Все эти значения на проводе ходят как hex-строки (длиной 64, 128, 128 и
64 символа соответственно).

### Зачем asyncio.to_thread

GOST-алгоритмы — чистый Python и заметно тяжёлые (особенно скалярное
умножение и Стрибог). Если вызвать их прямо в корутине, event loop
встанет. Поэтому `provider` оборачивает каждый вызов:

```python
return await asyncio.to_thread(sign, data, d, self.curve)
```

Это сохраняет интерфейс async/await и позволяет FastAPI продолжать
обслуживать другие соединения, пока считается одна подпись.

## Conversation key

Ключ беседы выводится **детерминированно** из отсортированной пары
`user_id` через Streebog-256:

```python
# backend/app/crypto/conversation.py
def conversation_key_material(a: int, b: int) -> bytes:
    lo, hi = sorted((a, b))
    return f"gost-demo-conv:{lo}:{hi}".encode("utf-8")

async def conversation_key(a: int, b: int) -> bytes:
    return await provider.hash(conversation_key_material(a, b))
```

Один и тот же модуль используется и серверными crypto-эндпоинтами
(`/seal`, `/unseal`, `/unseal-batch`), и сервисом вложений
([`services/attachment.py`](../backend/app/services/attachment.py)) —
поэтому картинки и тексты в одном диалоге шифруются на одном ключе.

> Это **учебный шорткат** вместо настоящего E2EE: сервер всегда может
> восстановить ключ. В боевой системе ключ выводился бы клиентами по
> ECDH (например, VKO ГОСТ 34.10), и сервер видел бы только шифртекст.
> См. [`security.md`](security.md).

| Алгоритм | Где «вызывается» |
| --- | --- |
| Стрибог-256 | `services/auth.py` (вывод ключа из пароля), `gost3410/signature.py` (хеш сообщения), `crypto/conversation.py` (ключ беседы), `routes/crypto.py` (fingerprint от сортированных pubkey) |
| ГОСТ 28147 + CTR | `services/auth.py` (шифрование приватного ключа), `routes/crypto.py` (seal/unseal сообщений), `services/attachment.py` (картинки) |
| ГОСТ 34.10 | `routes/crypto.py` (`seal` подписывает, `unseal`/`store_message` проверяют), `services/attachment.py` (подпись картинок) |
