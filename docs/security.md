# Безопасность

RubinChat — это **учебный** прототип. Документ ниже честно перечисляет,
что защищено, что защищено условно и что не защищено вовсе. Никакая
часть проекта не задумывалась как production-ready.

## Что реально работает

* **Пароли пользователей хранятся как bcrypt-хеши** с настраиваемой
  ценой раундов (`bcrypt_rounds`, по умолчанию 12). Утечка БД не даёт
  немедленный доступ к паролям.
* **Приватные ключи ГОСТ 34.10 хранятся зашифрованными паролем.** Ключ
  CTR выводится из пароля через Streebog-256. Сервер не знает пароль и
  не может расшифровать ключ без участия пользователя.
* **Все сообщения хранятся в БД только в шифрованном виде** (ГОСТ 28147
  CTR) и сопровождаются подписью ГОСТ 34.10. Сервер при приёмке
  проверяет подпись по сохранённому публичному ключу отправителя.
* **JWT** подписаны симметричным ключом (`JWT_SECRET`); время жизни
  ограничено `jwt_ttl_minutes` (по умолчанию 24 часа).
* **Защита от replay**: каждый принятый nonce запоминается в течение
  `nonce_window_seconds` (по умолчанию 300 секунд). Повтор пакета с тем
  же nonce отвергается.
* **Совместный safety-number** (`GET /api/crypto/fingerprint/{peer_id}`):
  Streebog-256 от отсортированных hex-строк публичных ключей обеих
  сторон. Алиса и Боб видят один и тот же код в профиле друг друга,
  и при подмене ключа MITM'ом коды не совпадут — это «out-of-band»
  верификация в духе Signal Safety Numbers.
* **Self-test ГОСТ-оптимизаций на старте**: `streebog.py` и `cipher.py`
  при импорте сравнивают T-табличные реализации с эталонными
  по-битно-идентичными версиями. При расхождении бэкенд не запустится —
  это страховка от silent corruption после правок крипто-кода.
* **Валидация ввода**: все JSON-схемы прописаны в Pydantic, длины
  hex-полей фиксированы, имена пользователей ограничены
  `[A-Za-z0-9_.-]`. На вложениях — две разные политики:
  * `kind=image` — узкий allow-list MIME (jpeg/png/webp/gif), чтобы
    превью в баббле не превратилось в SVG-инъекцию;
  * `kind=file` — чёрный список потенциально опасных типов
    (`text/html`, `application/xhtml+xml`, `application/javascript`,
    `text/javascript`, `application/x-msdownload`,
    `application/x-msdos-program`, `application/x-sh`) — иначе
    отправитель смог бы захостить XSS на нашем же origin через
    blob-URL получателя.

  Размер любого вложения ограничен 5 МБ, аватара — 2 МБ.
* **`X-Content-Type-Options: nosniff` на выдаче вложений** — закрывает
  старый трюк MIME-sniffing'а (Edge/IE мог увидеть HTML-теги в
  расшифрованном blob'е и решить, что это `text/html`, обходя
  `Content-Disposition: attachment`). Имя файла в `Content-Disposition`
  для не-картинок кодируется по RFC 5987 (`filename*=UTF-8''…`), чтобы
  кириллические имена доезжали без артефактов.

## Что работает условно

* **Нет настоящего сквозного шифрования (E2EE).** Эндпоинты
  `/api/crypto/seal` и `/api/crypto/unseal` — это серверные «обёртки»
  над ГОСТ-примитивами. Чтобы упростить курсовую часть, ключ беседы
  выводится **детерминированно** из пары `user_id` через Streebog-256.
  Сервер технически может расшифровать любую беседу. В настоящей
  системе вместо этого использовалось бы соглашение о ключе на
  стороне клиента (например, VKO ГОСТ 34.10).
* **Приватный ключ возвращается клиенту при логине.** Клиент должен
  где-то его держать, поэтому он живёт в `localStorage`. Любой XSS в
  страницу его украдёт.
* **CORS открыт на `*`** — для локальной разработки удобно, в проде
  следует ограничивать origin.
* **`JWT_SECRET` по умолчанию равен `change-me-in-production`.** Это
  явно указано в `.env.example` и в README.
* **Аватары хранятся в открытом виде** в колонке `users.avatar_data`.
  По смыслу они публичны — их видит каждый, кому показан профиль —
  но всё равно «лежат на сервере как есть», без ГОСТ-обёртки. Утечка
  БД раскроет картинки. Для отметки кеш-инвалидации используется
  инкрементируемый `avatar_version`.

## Чего сознательно не сделано

* Нет TLS — Compose поднимает HTTP на 8000. В проде нужен фронтящий
  reverse-proxy с сертификатом.
* Нет ограничения на частоту запросов (rate limiting) — ни на
  `/api/auth/*`, ни на `/api/messages/*`.
* Нет «прочитано/доставлено», нет подтверждения о доставке, нет
  retention-политики.
* Нет CSRF-защиты на REST: всё через `Authorization: Bearer ...`,
  cookie мы не используем — поэтому классический CSRF неактуален, но
  при добавлении cookie-аутентификации придётся вернуться к этому.
* JWT нельзя инвалидировать с серверной стороны (нет blacklist). Logout
  на клиенте просто стирает localStorage; токен «доживает» до `exp`.
* Реализации крипто **не constant-time** и не защищены от side-channel:
  тайминг-атаки, утечки кеша. Для учебного прототипа это нормально, для
  боевого — нет.
* Скалярное умножение ГОСТ 34.10 — простой double-and-add, без
  Montgomery ladder и без слепления.

## Модель угроз (что мы рассматриваем и что нет)

| Угроза | Защищаемся | Комментарий |
| --- | --- | --- |
| Пассивное чтение трафика | ❌ | Нужен TLS |
| Утечка БД | ◐ | Пароли — bcrypt; приватные ключи — зашифрованы паролем; сообщения — зашифрованы. Однако сервер знает ключ беседы, поэтому при компрометации сервиса в момент работы он мог бы читать. |
| Replay (повтор) пакета | ✓ | nonce-окно |
| Подделка сообщения от чужого имени | ✓ | проверка ГОСТ-подписи |
| MITM с активной модификацией | ◐ | Подпись ГОСТ 34.10 защищает от подмены тела сообщения, но **не** от подмены публичных ключей — для последнего служит safety-number, и сравнивать его нужно вручную через профиль |
| Brute-force паролей онлайн | ❌ | Нет rate limit |
| XSS в браузере | ❌ | localStorage достанется злоумышленнику |
| Утечка `JWT_SECRET` | ✗ | подделка любых JWT |

«✓» — есть защита; «◐» — частичная; «✗» / «❌» — нет.

## Если бы это шло в прод

Минимальный набор изменений:

1. Реальный E2EE: вычисление ключа беседы делает клиент (своя
   реализация ГОСТ 34.10 ECDH или VKO), сервер видит только
   шифртекст и подписи.
2. TLS-терминирование на reverse-proxy, HSTS, CSP.
3. Rate limit на login/register/messages.
4. Журналирование событий безопасности (вход, неудачные попытки,
   неуспешные подписи).
5. Хранилище nonce — Redis с TTL вместо in-memory словаря.
6. Тщательная проверка всего, что приходит в API: длины байтов, формат
   hex, лимиты на размеры payload.
7. Юнит-тесты с эталонными векторами всех трёх алгоритмов (RFC 6986,
   RFC 7836).
8. Перевод крипто-кода на `int.from_bytes`/`pow(...)`-инварианты с
   constant-time оговорками или замена на проверенную библиотеку с
   ГОСТ-сертификацией.
